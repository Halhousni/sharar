# Acquisition from a CED 1401: what is recovered, and what is not

`--record` opens a strip chart fed by a synthetic source. This note records how
far the real path got, so the next session starts from the evidence rather than
from the top.

**The hardware path is not implemented.** No 1401 is attached to this machine,
no capture of the wire protocol exists, and the device-level byte protocol was
not recovered from the driver. Everything below is what static analysis did
establish about where that protocol lives.

## The stack on Windows

```
spike2.exe / sonview.exe
  USE1432.dll        the 1401 API: U14Open1401, U14SendString, U14GetString, …
    DeviceIoControl(0x80012008, …)          one call per string transfer
      ced_us64.sys   WDM USB driver: finds the device, converts each IOCTL into
                     URBs, and owns the DMA engine and the handshake
        the 1401 on USB
```

The split matters for a port: everything a replacement needs is behind
`DeviceIoControl`, and on Linux that layer has to be rewritten, not wrapped.

## The character layer, as recovered

`USE1432.dll` works in short strings, not packets. From `U14SendString`
(0x3110) and `U14GetString`:

- a string is at most 0xff bytes; a longer one is refused with `0xfffffdf4`;
- the handle is an index 0..7 into a table at `0x1800090a0`; anything else is
  refused with `0xfffffe02`;
- the call blocks until the device reports room, polling `U14OutBufSpace` for
  up to a per-device timeout (values in a table at `0x180009158`) and then in
  25 ms steps, up to four times; running out of room forces a reset and fails
  with `0xfffffdb2`;
- the transfer is one `DeviceIoControl` with code `0x80012008`, the string as
  input and a 24-byte reply as output, of which the first two bytes are the
  status; a failed call or a short reply is `0xfd9e`;
- `U14SendChar` is `U14SendString` with a one-character string, and
  `U14GetChar` is `U14GetString` of two bytes, reporting `\n` for a zero.

The per-device error word at `0x180009128` is checked before the transfer and
returned instead of sending, which is how a driver-level fault surfaces as a
call-level failure.

## The IOCTL surface

`ced_us64.sys` decodes 33 codes, all `DeviceType 0x8001`, `METHOD_BUFFERED`.
The function numbers run from 0x802 to 0x2c0 in steps of four. What the dispatch
reaches, by code:

The DMA request decoder is 0x15e50. It splits the first byte of a request into
a four-bit command in the low nibble and a three-bit field in bits 4..6, sets
bit 6 of a flag word for command 8 and clears it otherwise, and treats only
commands 8 and 9 as the ones with a payload. That is the shape of the
`Esc`-framed DMA protocol the 1401 runs, but the meaning of the command numbers
was not recovered.

## What a port still needs

1. **The wire protocol.** The command numbers, the framing of a transfer area,
   and the reply codes. They are inside the driver's URB construction
   (0x124e0 and its callees), not in the IOCTL dispatch table above.
2. **A USB transport.** libusb against CED's vendor and product ids, bulk
   endpoints, and the same chunking the driver uses.
3. **A capture to check it against.** Without a 1401, or a Windows machine
   with one attached and USBPcap recording, none of the above can be verified.
   Static analysis can produce a hypothesis; only a capture can confirm it.
4. **The sampling configuration UI**, which is currently a label saying it needs
   the 1401.

Until 1 and 3 exist, `--record` keeps its synthetic source and the 1401 source
reports that no device is attached, which is the honest state: it is what the
program would say on this machine even if the transport were complete.
